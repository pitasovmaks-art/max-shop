## Таблица `user_map` — маппинг userId → chatId

```sql
CREATE TABLE user_map (
    user_id    BIGINT PRIMARY KEY,
    chat_id    BIGINT NOT NULL,
    created_at TIMESTAMP DEFAULT NOW()
);
```

Заполняется при каждом входящем сообщении от пользователя (если `userId ≠ chatId`).
Используется в `notifyCustomer` как fallback — если отправка по `tg_id` не прошла, ищем `chatId` в этой таблице.

## tg_id — как передаётся и хранится

### Из бота в приложение
- При `/start` и `bot_started` → `chat_id` берётся напрямую из `update.chat_id`
- Кнопка «Открыть магазин» → `web_app: SHOP_URL` (без параметров)
- При любом сообщении от пользователя → `userId` и `chatId` сохраняются в `user_map`

### В браузере (src/utils/tgid.js)
Функция `getTgId()` ищет по приоритету:
1. `?tg_id=` в URL
2. `?startapp=tg_id_...` в URL
3. `sessionStorage('tg_id')`
4. `localStorage('tg_id')` с TTL 24 часа

`saveTgId(id)` записывает во все три хранилища одновременно.

Файл подключается на всех страницах после `max-web-app.js`:
```html
<script src="/src/utils/tgid.js"></script>
```

### В заказе
`checkout.js` читает `getTgId()` и передаёт как `tgId` в тело POST `/api/orders`.

## Бот Max Messenger (`bot.js`)

- **Режим: webhook** — `POST /webhook`, регистрация при старте
- `API_BASE = 'platform-api.max.ru'`, токен без префикса Bearer

**Обработка событий:**
- `bot_started` → `addAdmin(chatId)` + приветствие с кнопкой магазина
- `message_created`:
  - Пропускаем `is_bot` сообщения
  - Сохраняем `userId → chatId` в `user_map` (fire-and-forget)
  - `/start`, `/myid`, `/reply` — команды
  - Не-администраторам: «Спасибо за сообщение! Теперь вы будете получать уведомления...» (простой текст, без кнопок)
  - Пересылка всем администраторам (кроме самого отправителя)

**Функции уведомлений:**
- `notifyStore(order)` — уведомление менеджеру при новом заказе
- `notifyCustomer(tgId, orderId, status, extra)`:
  - Пробует `sendMessage(+tgId, text)`
  - При ошибке → `GET /api/users/chat?user_id=tgId` → повторная попытка с найденным chatId

**HTTP helper `request()`:** теперь выбрасывает ошибку при HTTP 4xx/5xx (reject вместо resolve).

## Нерешённые задачи / известные проблемы

### Активные
- **tg_id в заказах** — основная проблема: `tg_id` попадает в заказ только если пользователь открыл магазин по ссылке из бота с `?tg_id=` в URL. Если URL параметр потерялся — `tgId` будет `null` и уведомления не дойдут. Пока нет надёжного способа получить `chat_id` из SDK Max Messenger.
- **user_map не всегда помогает** — маппинг строится только если `userId ≠ chatId` в входящем сообщении. Неизвестно, всегда ли они различаются в Max API. Нужна проверка на реальных данных из логов (`/myid`).
- **window.WebApp** — SDK подключён, но состав объекта неизвестен (нет документации локально). Нужно проверить в браузере — есть ли `initData`, `getUserInfo` или аналог.

### Технический долг
- Старые поля цен (`price`, `price_krd`, `price_msk`, `price_delivery`) не удалены из БД
- `price` в `product_variants` всегда сохраняется как 0
- `bot_admins.json` — все пользователи нажавшие /start считаются «администраторами» (список получателей пересылки). Нужно разделить на реальных менеджеров и просто подписчиков.

### Планируется
- Проверить логи после деплоя: структуру `update` при `/myid`, содержимое `window.WebApp`
- Если Max SDK передаёт user id — интегрировать в `getTgId()`
- Убрать `bot_admins.json` в пользу хардкода chat_id менеджеров в переменных окружения
- Тест уведомлений на реальном устройстве
