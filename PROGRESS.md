### 1. Схема БД (`schema.sql` + `server/db.js`, зеркально)

`product_variants` — новые колонки:
```
is_usd                     INTEGER NOT NULL DEFAULT 0   -- 0=₽ (как сейчас), 1=$
usd_price_krd_pickup       INTEGER NOT NULL DEFAULT 0   -- центы
usd_price_msk_pickup       INTEGER NOT NULL DEFAULT 0   -- центы
usd_sale_price             INTEGER NOT NULL DEFAULT 0   -- центы (своя для КРД-строки и для МСК-строки — скидка это одна колонка НА строку варианта, как и сейчас sale_price)
usd_delivery_surcharge_rub INTEGER NOT NULL DEFAULT 0   -- рубли, целиком (п.3: доставка = самовывоз МСК в $→₽ + эта наценка)
```
На `products` — никаких новых колонок (см. правку выше): $ только в `product_variants`, любой товар представлен хотя бы одним вариантом.

Новая таблица `usd_rate_history` (п.7, «больше ничего»):
```sql
CREATE TABLE IF NOT EXISTS usd_rate_history (
    id         SERIAL    PRIMARY KEY,
    rate       INTEGER   NOT NULL,  -- курс ×10000 (92.4567 -> 924567)
    prev_rate  INTEGER,             -- курс ×10000 до этого изменения, NULL у самой первой строки
    created_at TIMESTAMP NOT NULL DEFAULT NOW()
);
```
Текущий курс = последняя строка (`ORDER BY created_at DESC LIMIT 1`); если таблица пуста — считать курс не заданным (нет ни одного $-товара не может быть показан корректно до первой записи курса — это и будет проверено тестом).

Новая таблица `cart_sync` (п.10; правка — уникальность БЕЗ `city`, т.к. при каждой синхронизации строки пользователя полностью заменяются целиком, город хранится просто как текущий на момент последней синхронизации, а не как часть идентичности строки):
```sql
CREATE TABLE IF NOT EXISTS cart_sync (
    id            SERIAL    PRIMARY KEY,
    tg_id         BIGINT    NOT NULL,
    product_id    BIGINT    NOT NULL REFERENCES products(id) ON DELETE CASCADE,
    variant_label TEXT      NOT NULL DEFAULT '',
    city          TEXT      NOT NULL DEFAULT '',  -- 'krd' | 'msk', текущий город пользователя на момент синка
    qty           INTEGER   NOT NULL,
    price_seen    INTEGER   NOT NULL,  -- рубли; считает СЕРВЕР при синхронизации (pricing.js), не принимается от клиента
    updated_at    TIMESTAMP NOT NULL DEFAULT NOW(),
    UNIQUE (tg_id, product_id, variant_label)
);
```
Новая таблица `usd_notify_log` (ограничение «не чаще раза в сутки на человека», п.10):
```sql
CREATE TABLE IF NOT EXISTS usd_notify_log (
    tg_id       BIGINT    PRIMARY KEY,
    notified_at TIMESTAMP NOT NULL
);
```
В `orders.items[]` (JSON-поле, без миграции схемы) — добавить `priceUsdCents`/`rateX10000` к позиции, если она была $ на момент заказа; рублёвая `price` остаётся обязательной и единственной, которая участвует в сумме (п.11).

### 2. `server/utils/usdPrice.js` (новый, единая точка пересчёта — п.6)

- `centsAndRateToRub(cents, rateX10000)` — **без float**: `BigInt(cents) * BigInt(rateX10000)`, целочисленное деление-с-округлением-вверх на `BigInt(1_000_000 * 50)`, результат `× 50`, обратно в `Number`. Экспортирую и как основную функцию, и как основу для округления тестов (кратно 50, +1₽ случаи из п. тестов).
- `getCurrentRate()` / `getRateHistory()` — поверх `usd_rate_history`.
- `setRate(newRateX10000)` — вставляет новую строку (`prev_rate` = текущий курс), возвращает `{rate, prevRate, rateVersion}` (`rateVersion` = `id` новой строки — простая монотонная версия для п.8). **Не рассылает уведомления сама** — это отдельно (см. п.10 ниже), чтобы `usdPrice.js` оставался чистым пересчётом без побочных эффектов (тестируется в изоляции).
- `applyUsdToVariantRow(row)` — единственная точка пересчёта (колонок $ на `products` нет, см. правку выше). Если `is_usd=0`, возвращает рублёвые поля как есть (рублёвые товары не трогаются, п.1); если `is_usd=1`, считает `priceKrdPickup`/`priceMskPickup`/`salePrice` через `centsAndRateToRub`, и `priceMskDelivery = priceMskPickup_рубли + usdDeliverySurchargeRub` (п.3 — формулу скидки на доставке в `effectiveItemPrice` НЕ меняю, она уже всё посчитает правильно, если туда придут верно посчитанные рублёвые `priceMskPickup`/`priceMskDelivery`/`salePriceMsk`).

### 3. `server/utils/pricing.js` / `server/routes/orders.js`

- `loadProductsForPricing()` — после загрузки строк вариантов пропускать каждую через `applyUsdToVariantRow` (текущий курс грузится один раз на вызов). `resolveOrderItem()` не меняется вообще — он уже получает рублёвые `fresh.*` поля, просто теперь они могут быть результатом конвертации, а не сырыми колонками.
- `resolveOrderItem()` дополнительно возвращает `priceUsdCents`/`rateX10000`, если позиция была $ (для сохранения в заказ, п.11).
- `POST /api/orders` (п.9): после пересчёта `realTotal` — **сравнить с присланным клиентом `total`**; при несовпадении — `409` с телом `{ error:'price_changed', items: realItems, total: realTotal }`, заказ не создавать. При совпадении — всё как сейчас, плюс `priceUsdCents`/`rateX10000` в сохраняемый JSON позиции, если были.
- Оформленные заказы (п.11) — больше никогда не трогаются: ни один из новых путей (смена курса, пересчёт каталога) не задевает таблицу `orders` вообще, только `product_variants`/`products`/`usd_rate_history`. Тест на это — отдельным пунктом ниже.

### 4. `server/routes/products.js`

- `normalizeVariant()` — применяет `applyUsdToVariantRow` **до** сборки camelCase-ответа (рубли в тех же существующих полях, как и просил п.6); `normalize()` (уровень товара) не меняется — $-колонок там нет. Дополнительно, **только если вызов от админа** (флаг в `attachVariants`/`normalize`, т.к. публичный `GET /api/products` вызывается без `requireAdmin`) — `normalizeVariant()` добавляет сырые `$`-поля (`isUsd`, `usdPriceKrdPickup` и т.п.) для формы редактирования.
- `POST /api/products/import` — новые колонки «Цена КРД $» / «Цена МСК $» / «Наценка доставка ₽» / «Скидка $» (алиасы `priceKrdPickupUsd`/`priceMskPickupUsd`/`deliverySurchargeRub`/`salePriceUsd`, по аналогии с уже существующими алиасами). Валидация на уровне строки (п.12): если в одной строке одновременно заполнены рублёвые (`priceKrdPickup`/`priceMskPickup`/`priceMskDelivery`) И $-колонки — строка целиком идёт в `errors` (та же структура `{row, reason}`, что и сейчас), товар/вариант не создаётся. INSERT в `product_variants` — доп. колонки `is_usd`/`usd_*`, по аналогии с текущими двумя `INSERT` (КРД/МСК) в цикле импорта.
- Новый `GET /api/products/export` (admin-only, без S3, подтверждено) — собирает все товары+варианты, строит `.xlsx` в памяти (`xlsx`, уже в зависимостях) **в точности с теми же колонками**, что ждёт импорт (включая $-колонки), отдаёт как `Content-Disposition: attachment`. Цель — «выгрузил → поправил → загрузил обратно» без ручного пересобирания структуры файла.
- `PUT /api/products/:id/variants` — принимает и сохраняет `isUsd`/`usdPriceKrdPickup`/`usdPriceMskPickup`/`usdSalePrice`/`usdDeliverySurchargeRub` по аналогии с текущими полями; существующая логика уведомления о старте акции (`sale_price>0` → `notifyPromo` подписчикам) должна сработать и для $-скидки — проверка «акция началась» должна смотреть не только на `sale_price>0`, но и на `usd_sale_price>0` при `is_usd=1`.

### 9. Синхронизация корзины + уведомления

**Клиент — новый общий модуль `src/shared/cartSync.js`** (одна функция, не 6 копий; `src/shared/` уже существует — там сейчас `escHtml.js`/`bannerRender.js`/`sellerConfig.js`). Экспортирует одну функцию `syncCartToServer(cart)`:
  - читает `localStorage.getItem('city')` (`'krd'|'msk'`, тот же ключ, что уже использует `cart.js`/`checkout.js`),
  - шлёт `POST /api/cart-sync` с `{ items: cart.map(i => ({productId, variantLabel, qty})), city }` вместе с подписанной `initData` (как у `favorites.js`) — **без `priceSeen`**: цену клиент не присылает вообще, это правка — сервер считает её сам (ниже);
  - fire-and-forget (`fetch(...).catch(() => {})`) — ошибка синхронизации не должна блокировать саму работу с корзиной.

Вызывается из **всех 6 мест**, где корзина сейчас пишется в `localStorage` (нашёл все explicit-grep’ом, дублирования `saveCart` не убираю — это отдельный, незапрошенный рефакторинг, только добавляю вызов рядом):
  1. `src/catalog/catalog.js:231` (`saveCart`)
  2. `src/catalog/product.js:19` (`saveCart`)
  3. `src/favorites/favorites.js:15` (`saveCart`, добавление в корзину из избранного)
  4. `src/orders/orders.js:400` («Повторить заказ»)
  5. `src/cart/cart.js:11` (`saveCart` — изменение qty/удаление/очистка корзины на странице корзины)
  6. `src/cart/checkout.js:525` (`localStorage.removeItem('cart')` после оформления заказа — здесь `syncCartToServer([])`, т.е. очистка и на сервере)

**Сервер — `server/routes/cart-sync.js` (новый), `bot.js`, cron (в `server/index.js`, по образцу уже существующих `ozonSync`/`agentBot`), `privacy.html`:**
- `POST /api/cart-sync` (`requireUser`) — правка: это полная замена, а не upsert. В одной транзакции (`db.inTransaction`, как уже используется в проекте, напр. в импорте товаров): `DELETE FROM cart_sync WHERE tg_id=$1`, затем по каждому пришедшему item — `price_seen` считает **сервер**, той же функцией, что и для заказа (`loadProductsForPricing` + `effectiveItemPrice(fresh, city, null)` из `pricing.js` — `null` как метод доставки, ровно как сейчас считает сама страница корзины для отображения, см. `cart.js`), и только с этой посчитанной ценой строка вставляется. Присланная клиентом цена нигде не используется и даже не читается. Пустой `items` = очистка (п.6 выше). `tg_id` только из подписанных `initData`, никогда из тела.
- Периодическая очистка (`node-cron`, по образцу `services/ozonSync.js`, ежедневно): `DELETE FROM cart_sync WHERE updated_at < NOW() - INTERVAL '14 days'`.
- После `setRate()` (смена курса администратором) — пройтись по `cart_sync`, сгруппировать по `tg_id`, для каждого человека пересчитать текущую цену позиций той же `effectiveItemPrice(fresh, city, null)`, сравнить с сохранённым `price_seen`; если хоть одна цена изменилась (в любую сторону) — одно сообщение (по образцу `bot.js:notifyStock`, с тем же fallback через `/api/users/chat`) со списком позиций и `было → стало`; не чаще раза в сутки на `tg_id` — проверка `usd_notify_log` до отправки.
  - **Если сообщение реально отправлено** — `price_seen` у всех пересчитанных строк этого `tg_id` обновляется на новую цену (иначе то же изменение попадёт в уведомление повторно).
  - **Если отправка пропущена из-за суточного лимита** — правка: `price_seen` НЕ обновляется, строки остаются со старой ценой, чтобы при следующей проверке (завтра, когда лимит уже не действует) разница с реальной ценой всё ещё была видна и уведомление не потерялось.
- `privacy.html`, раздел 2 («Какие данные мы собираем») — строка про то, что состав корзины (товар, вариант, город, количество) синхронизируется на сервер для уведомлений об изменении цены; раздел 5 (срок хранения) — срок 14 дней без изменений для этих данных.

## Правила разработки

- **Версионирование статики (`?v=...`).** Все `<script src>`/`<link rel="stylesheet">` в `index.html`/`catalog.html`/`admin/index.html` и `@import url('/src/theme.css?v=...')` в `src/catalog/catalog.css` подключены с query-параметром `?v=...`. Эти файлы кэшируются браузером агрессивно и без ревалидации (`Cache-Control: public, max-age=31536000, immutable` — выдаётся `server/index.js` любому `.js`/`.css`-запросу с `?v=` в URL). **При любом изменении содержимого такого `.js`/`.css` обязательно поднимать номер `?v=...` во всех местах, где файл подключён — иначе у пользователей на год останется старая закэшированная версия, и правка до них не дойдёт.** Сам HTML не кэшируется (`Cache-Control: no-cache`) — новая версия долетит сразу после деплоя, но только если номер в `?v=` действительно был поднят. Файл, который ни разу не менялся с момента появления версионирования, может законно отставать номером от остальных — это нормально, важно лишь поднимать номер именно при изменении. Исключения: `https://st.max.ru/js/max-web-app.js` (внешний файл Max, не наш) и несколько файлов в `admin/` (`categories.js`, `stores.js`, `banners.js`, `admin.css`), которые по сложившейся в админке конвенции подключены вообще без `?v=` — у них просто безопасный дефолтный кэш (`public, max-age=0`, всегда с ревалидацией по ETag), версионировать их не обязательно.

## Сессия 23.10.2026 — TRUST_PROXY_HOPS подтверждён на проде, временный лог убран

`server/index.js` после слияния 21.10.2026 читал число доверенных прокси из `TRUST_PROXY_HOPS` (дефолт `1`, то же значение, что было захардкожено) и временно логировал `req.ip`/`X-Forwarded-For` на каждый `/health`, чтобы подтвердить это число на реальном деплое перед тем, как снимать временный лог.

Вывод: Timeweb стоит перед приложением ровно одним хопом, и заголовок с его стороны доверенный (клиент не может его подделать) — `TRUST_PROXY_HOPS=1` подтверждён как верное значение.

Временный блок логирования на `/health` удалён — `TRUST_PROXY_HOPS` остаётся в env (переопределяемым, дефолт `1`), но теперь без постоянного логирования IP на каждый запрос.

### Сделано — `fix-navigation-speed`

Диагностика (без изменения кода) на временном сервере через headless Chrome (CDP) с эмуляцией медленной сети показала: нет сжатия ответов нигде; все `.js`/`.html` отдавались с `Cache-Control: no-store` несмотря на то, что уже были версионированы (`?v=...`); каталог (категории/подкатегории/товары) не кэшировался на клиенте и перезапрашивался при каждом переходе; 4 скрипта в `<head>` и `catalog.js` (54KB) в конце `body` — без `defer`, блокируют разбор страницы; фон не задан в `<head>` (белая вспышка между документами); пустые блоки вместо скелетонов; нет prefetch соседней страницы.

Исправлено (от простого к сложному, бизнес-логика и проверка доступа не трогались):
- сжатие (gzip/brotli) всех ответов — пакет `compression`;
- заголовки кэша: HTML/API → `no-cache` (дешёвая ревалидация по ETag вместо полной перекачки), версионные `.js`/`.css` → `public, max-age=31536000, immutable` (см. «Правила разработки» выше);
- клиентский кэш каталога в `localStorage` (stale-while-revalidate: сохранённые данные — сразу на экран, обновление — тихо в фоне; при ошибке фона — молча остаёмся на кэше);
- `defer` на все 7 скриптов, включая `shopGuard.js` (относительный порядок выполнения не изменился — проверено оба пути: валидный доступ работает, невалидный по-прежнему блокируется "Not Found");
- фон страницы — инлайновый `<style>` в `<head>`, до загрузки `catalog.css`;
- скелетоны вместо пустых блоков в рельсе категорий и сетке товаров (`#catRail`, `#productsGrid`);
- prefetch соседней страницы (Главная↔Каталог) по появлению ссылки в viewport (`IntersectionObserver`) и по `pointerdown`;
- `<meta name="view-transition" content="same-origin">` — не ломает браузеры без поддержки.

Эффект (синтетические данные, тот же профиль сети, до → после): повторная загрузка Главной — 230.9KB/19 запросов → 10.9KB/20 запросов; переход Главная→Каталог — 87.4KB → ~2.3–2.9KB; `catalog.js` по сети — 54.5KB → 16.9KB; `/api/products` (демо-данные) — 145KB → ~7.2KB.

### Не сделано и почему

- **`shopGuard.js` остаётся синхронным блокирующим XHR** (`xhr.open(..., false)` к `/api/auth/verify` на каждой загрузке страницы) — не трогали сознательно, задача прямо требовала не ослаблять проверку доступа. `defer` изменил только момент его выполнения (после разбора HTML, а не во время), не то, что он блокирует.
- **Замеры сделаны не в реальном Max Messenger, не на рабочей БД.** Расширение Claude in Chrome было недоступно в этой сессии, локального Postgres тоже нет — поднимался временный сервер с синтетическим каталогом (140 товаров правдоподобного размера) и временно подменённым на уровне загрузчика Node драйвером `pg` (сам `node_modules/pg` не трогался), по нему гонялся headless Chrome через CDP с эмуляцией сети (Fast 3G: 150мс, 1.6/0.75 Мбит/с). Цифры показывают реальный эффект самих изменений (сжатие, кэш-заголовки), но абсолютные миллисекунды на проде с реальными данными и в реальном Max WebView будут другими — стоит перепроверить после деплоя.

## tg_id — как передаётся и хранится

### Из бота в приложение
- При `bot_started` → `chat_id` берётся из `update.chat_id`
- При любом сообщении → `userId` и `chatId` сохраняются в `user_map`

### В браузере (`src/utils/tgid.js`)
Функция `getTgId()` ищет по приоритету:
1. `?tg_id=` в URL
2. `?startapp=tg_id_...` в URL
3. `sessionStorage('tg_id')`
4. `localStorage('tg_id')` с TTL 24 часа

### В заказе
`checkout.js` читает `getTgId()` и передаёт как `tgId` в тело `POST /api/orders`.

## Боты Max Messenger

### Основной бот (`bot.js`) — `id635009278943_bot`
- **Режим: webhook** → `POST /webhook`
- `bot_started` → приветствие с кнопкой магазина, `addAdmin(chatId)`

### Бот поддержки (`bot-support.js`) — `id635009278943_1_bot`
- **Режим: webhook** → `POST /webhook-support`
- Запускается через `startSupportBot()` внутри той же `.then()` цепочки что и основной бот, обёрнут в `try/catch`
- Менеджеры определяются по `user_id` (одинаков у обоих ботов): `SUPPORT_ADMIN_USER_IDS = [5149723, 100067838]`

- Ответ менеджера:
  - **Свайп-reply** на пересланное сообщение (через `msg.link.type === 'reply'`, извлекает ID из текста `🆔 ID: ...`)

## Известные проблемы / технический долг

- **⚠️ `tg_id` не проверяется против `initData`** (заказы, избранное, уведомления о поступлении) — подробности и план исправления в «Сессия 30.09.2026» выше. Самый серьёзный пункт в этом списке: чужие персональные данные (заказы), а не просто неудобство.
- **tg_id в старых заказах** — заказы #1–23 без tg_id, уведомления не дойдут, не чинится
- **user_map vs chat_id** — маппинг строится только если пользователь писал боту. Если не писал — fallback не сработает
- **Старые поля цен** (`price`, `price_krd`, `price_msk`, `price_delivery` на уровне товара и варианта) — не удалены, используются как фолбэк
- **bot_admins.json** — все кто нажал `/start` считаются получателями пересылки. Нужно разделить на менеджеров и подписчиков
- **SIGTERM в логах при деплое** — нормальное завершение старого процесса, не проблема
- **Фото в корзине** — сохраняется только при добавлении через каталог; товары добавленные до этого коммита фото не имеют
