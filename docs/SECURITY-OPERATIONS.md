# Безопасность и эксплуатация

## Перед деплоем ветки security-hardening

1. Сохранить резервную копию рабочей БД штатным механизмом Timeweb, затем проверить её восстановление в отдельную тестовую БД. Доступа к панели/боевой БД у локального разработчика нет: наличие копий не подтверждено.
2. Вебхуки обоих ботов автоматически получают разные секреты при старте. По умолчанию секрет вычисляется HMAC-SHA256 из токена конкретного бота и метки назначения. Токен бота не передаётся как webhook secret. Новые обязательные переменные не нужны. При желании задать WEBHOOK_SECRET / SUPPORT_WEBHOOK_SECRET (16–256 букв, цифр, `_`, `-`). На деплое старые события без заголовка временно получают 401 до успешного обновления подписки; Max повторяет доставку. Ошибки регистрации повторяются через минуту. При откате сначала учитывать, что прежняя версия не проверяет секрет.
3. Старые записи получателей поддержки перед пересылкой проверяются через Max GET /chats/{id}: только личный диалог с разрешённым менеджером. Чужие/групповые/непроверенные записи не используются. Результат кэшируется на 10 минут. Проверить реальную совместимость API и заново открыть поддержку обоим менеджерам; при ошибке API пересылка временно не выполняется (fail closed).

После деплоя: в логах обоих ботов должна быть успешная регистрация, а /readyz должен возвращать 200. Затем с реального Max отправить сообщение в магазинного бота и поддержку. Не делать тестовые поддельные POST на боевой webhook.
4. Новые таблица notification_outbox и колонка orders.client_request_id аддитивные, добавляются в schema.sql и db.js. Старые заказы не изменяются. Миграции и доступность БД необходимы для /readyz.
5. Тестовые сценарии на iPhone/Max: поиск и назад; смена города; избранное и корзина; заказ самовывоз/город/СДЭК/Ozon; вариант гарантии/цена остаются прежними; ремонт; уведомления обоим менеджерам. Результат локальных заглушек не заменяет эту проверку.

## Сертификат PostgreSQL

Режим совместимости без CA пока сохраняет прежний TLS с отключённой проверкой и выводит предупреждение. Автоматического понижения после ошибки в строгом режиме нет.

1. В Timeweb → PostgreSQL → Подключение скачать публичный корневой сертификат именно этого кластера. Это не приватный ключ. Справка: https://timeweb.cloud/docs/dbaas/postgresql/connect-to-database
2. Указать DB_SSL_CA (PEM, поддерживаются буквальные `\n`) либо DB_SSL_CA_FILE (путь к файлу в контейнере). Это автоматически включает rejectUnauthorized=true. Для публично доверенного сертификата без собственного CA достаточно DB_SSL_VERIFY=true. Использовать hostname из панели, совпадающий с сертификатом.
3. Сначала проверить подключение с этим CA вне работающего приложения. Затем применить переменную и проверить /readyz, чтение каталога и создание тестового заказа.
4. До выполнения этих шагов пункт проверки сертификата БД не считать закрытым. Не заменять сертификат случайным CA из интернета.

## Очередь уведомлений менеджерам

Создание заказа/ремонта и задания уведомления — одна транзакция. Worker берёт задания с lease и SKIP LOCKED, переживает рестарт, делает до 12 попыток с увеличивающимся интервалом. Просроченный lease можно повторить после 5 минут. После 12 неудач задание сохраняется, не исчезает. Семантика at-least-once: если Max принял сообщение, а процесс упал до отметки доставки, возможен дубль. При частичном сбое двух получателей повтор может повторно доставить успешному получателю. Клиентские статусные/рекламные сообщения этой очередью пока не покрыты.

GET /api/admin/health (действующий Bearer-токен админки) показывает pending, failed и oldest_pending. История успешных заданий очищается через 30 дней. Личных данных в очереди нет, только тип и ID сущности. Системный монитор должен оповещать при failed > 0 или зависании заданий более 15 минут; не ограничиваться /health, который проверяет только живость процесса.

## Резервные копии

Штатные копии Timeweb — первый уровень защиты. Дополнительная копия: `npm run backup`, запускать внешним планировщиком раз в сутки. Нужны установленный pg_dump совместимой версии, DB_* и S3_* из окружения, проверяемый TLS PostgreSQL, BACKUP_BUCKET и BACKUP_ENCRYPTION_KEY. Для pg_dump сертификат задаётся файлом DB_SSL_CA_FILE.

- BACKUP_BUCKET — отдельный непубличный бакет, не бакет фотографий. Права сервисного ключа: запись в backup-бакет и чтение/копирование products/ и banners/ исходного бакета. Убедиться, что нет политики публичного чтения.
- BACKUP_ENCRYPTION_KEY — 32 случайных байта в base64. Сгенерировать локально `openssl rand -base64 32`, сохранить в менеджере паролей отдельно от бакета. Значение не публиковать. Без этого ключа восстановление БД невозможно.
- Скрипт создаёт согласованный pg_dump custom, шифрует AES-256-GCM и загружает приватно. Фотографии копируются отдельными приватными объектами. Они защищены доступом бакета, не шифруются этим ключом на стороне клиента. manifest.json записывается последним: его отсутствие означает незавершённую копию.
- Временные файлы находятся в каталоге 0700 и удаляются при нормальном завершении/ошибке. При аварийном выключении контейнера остаётся риск временного нешифрованного dump: используйте одноразовый runner/зашифрованный диск, не общий tmp-хост. В S3 БД отправляется только зашифрованной.
- Настроить lifecycle приватного backup-бакета: например 30 дней после выбора владельцем срока хранения. Код сам копии не удаляет. Не включать удаление до проверки восстановления.
- Выполнить `npm run backup:verify -- /путь/database.dump.enc` с тем же ключом и pg_restore. Это проверяет аутентичность и структуру архива, но НЕ является доказательством восстановления.
- Реальная проверка: скачать полную копию, расшифровать в изолированном окружении, восстановить через pg_restore в НОВУЮ тестовую БД (никогда поверх боевой), сверить товары, варианты, заказы, ремонты и наличие скопированных изображений по manifest. На время проверки тестовый сервер должен иметь пустые токены ботов/отключённые workers, чтобы не рассылать сообщения. Удалить тестовые персональные данные после проверки.

## Мониторинг

- Внешний HTTP-монитор каждые 5 минут: HTTPS `/readyz`, ожидать 200; настроить уведомление владельцу. На старте до инициализации схемы и при ошибке БД возвращается 503, без подробностей/секретов.
- `npm run health:check` проверяет /readyz с тремя попытками и timeout, выходит с ненулевым кодом при проблеме. SHOP_URL должен указывать на нужное окружение.
- Если runner имеет ADMIN_PASSWORD, дополнительно проверяет защищённое состояние очереди. Пароль/токены не передавать аргументами команд и не писать в логи. Выход с ненулевым кодом должен обрабатываться планировщиком/системой мониторинга; сам скрипт сообщения не отправляет.
- Ежедневно проверять успех backup-job и наличие manifest. Один только зелёный /readyz не доказывает сохранность резервных копий.

## Excel

Импорт ограничен 5000 строками, файл в админке — 10 МБ. Предварительный просмотр до подтверждения не меняет БД. Дубли по нормализованным бренду/артикулу или названию/категории пропускаются, конкурентные импорты сериализуются. Существующие товары не перезаписываются. Предпросмотр не резервирует данные: если каталог изменился до подтверждения, реальный импорт повторно проверяет дубли. Скидки/цены не придумываются. Фотографии из Excel этот этап не импортирует.

## Откат

Только git revert коммитов ветки после согласования, не reset/force-push. Аддитивные таблицы/индексы можно оставить: старый код их не использует. Перед откатом worker проверить pending-уведомления: старый код не обслуживает очередь. Не удалять задания и не откатывать зависимости до известных уязвимых версий без осознанного решения.
